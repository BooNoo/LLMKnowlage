# Workspace Knowledge Base

Этот workspace — **хранилище знаний** (knowledge base), которые мы раскапываем по ходу работы.
Здесь лежат документы по разным сферам: то, что выяснили, проверили и не хотим выяснять заново.

Документы — plain-text Markdown, живут в git, читаются и человеком, и агентом.

> **Главное правило:** нет записи в индексе ниже — считай, что знания не существует.
> Любой новый или изменённый документ обязан отразиться в разделе [«Индекс знаний»](#индекс-знаний).

---

## 1. Что здесь храним

- ✅ **Знания, а не задачи.** «Как устроено», «как работает», «как делать правильно», а не «сделать к пятнице».
- ✅ **Проверенные факты.** Если факт получен из исходников или на живом инстансе — так и пишем («проверено на…»).
- ✅ **Грабли и подводные камни.** Самая ценная часть: то, что стоило времени.
- ✅ **Рецепты и команды**, которые реально работают.
- ❌ **Секреты** (токены, пароли, ключи) — никогда в файлы.
- ❌ **Мусор.** Скриншоты без текста, черновики, «TODO разобраться» без контекста, копипаста без вывода.

## 2. Структура

Пока всё плоско — файлы в корне, имя в `kebab-case`, расширение `.md`, один документ = одна тема.

```
WorkspaceLLMKnowlage/
├── README.md            ← правила + индекс (этот файл)
├── .gitignore           ← macOS-мусор и секреты
├── <тема>.md            ← документ знания
└── ...
```

Если сфер станет много — разносим по папкам (`dsh/`, `bruno/`, ...), но индекс всё равно остаётся
**один** — в этом README.

## 3. Правила работы

### 3.1 Добавление нового документа

1. Создать `<тема>.md` с заголовком `# <Тема> — <подзаголовок>`.
2. В начале документа — блок `>` со статусом: откуда знания, на чём проверено, что ещё не сделано.
3. Добавить строку в **Индекс знаний** (раздел 4): файл + сфера + summary + статус.
4. Если документ связан с другими — поставить кросс-ссылки `[имя](./файл.md)` в начале и в индексе.

### 3.2 Изменение существующего документа

- **Смысл не поменялся** (опечатки, уточнения, новые примеры) — README не трогаем.
- **Смысл значительно поменялся** (новый раздел, другой вывод, другая версия софта) — обновить **summary** в индексе.
- **Файл переименован** — обновить имя в индексе **и все кросс-ссылки** на него (`grep` по старому имени).
- **Документ устарел целиком** — не удалять молча: пометить в начале `> ⚠️ Устарело, см. <ссылка>` и поправить статус в индексе.

### 3.3 Формат summary в индексе

Summary отвечает на вопрос **«что я узнаю, если открою этот файл»**, а не «о чём он».

- 1–3 предложения, по делу, без воды.
- Лучше перечислить конкретику: методы, команды, ограничения, грабли.
- Плохо: «Документ про Bruno».
- Хорошо: «Формат OpenCollection YAML, WebSocket-запросы, разница Secrets/Variables, CLI, грабли с токеном».

### 3.4 Гигиена

- Один факт — в одном месте. Дубли разъезжаются и врут.
- Внутри документа — ссылки на источники (файл исходника, версия, URL).
- `.DS_Store` и прочее от macOS в git не коммитим (см. `.gitignore`).
- Версии софта указываем явно: знания без версии быстро гниют.

## 5. Git

Ветка — `main`, remote — `origin` → <https://github.com/BooNoo/LLMKnowlage> (**публичный**).

**Куда коммитим:** только документы знания + `README.md` + `.gitignore`.
**Что не коммитим никогда:** секреты, токены, `*.local`, `.env*` — они в `.gitignore`, но всё равно проверяй `git diff --cached` перед коммитом. Репозиторий публичный: попавший в историю токен считается скомпрометированным (его нужно отзывать, а историю переписывать).

**Соглашения:**

- Один коммит = одно смысловое изменение (новый документ / правка темы / реструктуризация).
- Сообщения — по-русски, императив, с областью:
  - `docs: добавить <тема>.md` — новый документ
  - `docs(<тема>): <что уточнили>` — правка документа
  - `index: обновить индекс под <тема>` — правка только README
  - `chore: ...` — инфраструктура репозитория
- Если коммит добавляет или переименовывает документ — **в том же коммите** правка индекса в README.
  Ревизор этого не проверит, но именно так индекс не расходится с реальностью.

**Полезное:**

```sh
git status --short          # что изменилось
git diff                    # построчная проверка перед коммитом
git log --oneline --stat    # история изменений знаний
git grep -n "старое-имя"    # найти битые ссылки после переименования
```
